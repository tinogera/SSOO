### Bugs identificados

**Bug 1 — Handler `MSG_CREAR_SEGMENTO` cuando necesita compactación (`kernel_memory/src/main.c:774`):**

Flujo actual (roto):
```
KS envía MSG_CREAR_SEGMENTO → KM detecta que necesita compactar
→ KM envía MSG_COMPACTAR a fd_ks               (correcto)
→ KM envía MSG_COMPACTAR a fd (el caller = KS)  ← BUG: responde con mensaje incorrecto
→ No espera MSG_FIN_COMPACTACION antes de responder
```

El KS que espera la respuesta a `MSG_CREAR_SEGMENTO` recibe `MSG_COMPACTAR` como respuesta — no sabe qué hacer con eso. El `thread_km_listener` del KS enruta `MSG_COMPACTAR` a `handle_compactar()`, pero el hilo que envió `MSG_CREAR_SEGMENTO` queda colgado esperando `MSG_TABLA_SEGMENTOS`.

Flujo correcto:
```
KS envía MSG_CREAR_SEGMENTO → KM detecta que necesita compactar
→ KM envía MSG_COMPACTAR a fd_ks
→ KM espera MSG_FIN_COMPACTACION (en el mismo hilo o con un condvar interno)
→ KM reintenta crear_segmento
→ KM responde MSG_TABLA_SEGMENTOS al KS
```

**Bug 2 — Handler `MSG_FIN_COMPACTACION` envía mensaje extra (`kernel_memory/src/main.c:872`):**

```c
enviar_mensaje(fd, MSG_OK, NULL, 0);             // correcto: KS espera MSG_OK
if (fd_ks >= 0) enviar_mensaje(fd_ks, MSG_FIN_COMPACTACION, NULL, 0);  // ← BUG
```

`fd` y `fd_ks` apuntan al mismo KS. El segundo `enviar_mensaje` manda un `MSG_FIN_COMPACTACION` inesperado al KS justo cuando este ya procesó el `MSG_OK` y reencola los procesos. Eso puede hacer que `thread_km_listener` del KS procese un `MSG_FIN_COMPACTACION` fantasma y llame de nuevo a `handle_compactar()`.

**Fix sugerido para ambos bugs:** en el handler de `MSG_CREAR_SEGMENTO`, cuando `res == 1`:
1. Enviar `MSG_COMPACTAR` a `fd_ks`.
2. Bloquear con un semáforo interno hasta que `MSG_FIN_COMPACTACION` llegue al hilo del KS (manejar en la misma conexión con un flag/condvar global en KM).
3. Después de la compactación, reintentar `crear_segmento`.
4. Responder al caller con `MSG_TABLA_SEGMENTOS` o `MSG_ERROR`.
5. En `MSG_FIN_COMPACTACION` handler: eliminar la segunda línea de `enviar_mensaje(fd_ks, ...)`.

### Paso 1 — Luciano: fixes en KM (directo en develop)

Sin dependencias. Dos cambios puntuales en `kernel_memory/src/main.c`.

**Fix A — handler `MSG_CREAR_SEGMENTO` cuando necesita compactar (`main.c:774`):**

Problema: cuando `crear_segmento` retorna 1 (necesita compactación), KM envía `MSG_COMPACTAR` al KS pero inmediatamente responde `MSG_COMPACTAR` al caller sin esperar que termine. El KS recibe una respuesta inesperada a `MSG_CREAR_SEGMENTO`.

Solución:
1. Agregar un semáforo/condvar interno en KM para que el hilo de `MSG_CREAR_SEGMENTO` se bloquee hasta recibir `MSG_FIN_COMPACTACION`.
2. El handler de `MSG_FIN_COMPACTACION` señala ese semáforo/condvar después de compactar.
3. El hilo bloqueado se despierta, reintenta `crear_segmento` y responde `MSG_TABLA_SEGMENTOS`.

```c
// Reemplazar en el handler de MSG_CREAR_SEGMENTO (res == 1):
if (fd_ks >= 0) enviar_mensaje(fd_ks, MSG_COMPACTAR, NULL, 0);
enviar_mensaje(fd, MSG_COMPACTAR, NULL, 0);  // ← eliminar esta línea

// Por:
if (fd_ks >= 0) enviar_mensaje(fd_ks, MSG_COMPACTAR, NULL, 0);
sem_wait(&sem_compactacion_lista);           // bloquear hasta que KS termine
res = crear_segmento(ctx, id_seg, tamanio); // reintentar
// luego responder MSG_TABLA_SEGMENTOS o MSG_ERROR normalmente
```

**Fix B — handler `MSG_FIN_COMPACTACION` envía mensaje extra (`main.c:878`):**

Problema: después de responder `MSG_OK` al KS, envía un `MSG_FIN_COMPACTACION` extra que puede disparar una segunda compactación.

Solución: eliminar la segunda línea y señalar el semáforo interno en su lugar.

```c
// Reemplazar:
enviar_mensaje(fd, MSG_OK, NULL, 0);
if (fd_ks >= 0) enviar_mensaje(fd_ks, MSG_FIN_COMPACTACION, NULL, 0);  // ← eliminar

// Por:
enviar_mensaje(fd, MSG_OK, NULL, 0);
sem_post(&sem_compactacion_lista);  // despertar al hilo que espera en MSG_CREAR_SEGMENTO
```
