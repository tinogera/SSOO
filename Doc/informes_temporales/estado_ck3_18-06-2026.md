### Bugs corregidos (18/06/2026 — commits `bb330c0` y `24f5a95`)

Los cuatro bugs del KM fueron corregidos directamente en develop por Nicolas. Cada cambio incluye comentarios `// NOTA LUCIANO [...]` para que Luciano pueda entender y revisar las modificaciones.

**Bug 1 — Handler `MSG_CREAR_SEGMENTO` cuando necesita compactación** — ✅ CORREGIDO

Flujo original (roto):
```
KS envía MSG_CREAR_SEGMENTO → KM detecta que necesita compactar
→ KM envía MSG_COMPACTAR a fd_ks               (correcto)
→ KM envía MSG_COMPACTAR a fd (el caller = KS)  ← BUG: responde con mensaje incorrecto
→ No espera MSG_FIN_COMPACTACION antes de responder
```

Flujo corregido:
```
KS envía MSG_CREAR_SEGMENTO → KM detecta que necesita compactar
→ KM envía MSG_COMPACTAR a fd_ks
→ KM bloquea con sem_wait(&sem_compactacion_lista)
→ (MSG_FIN_COMPACTACION llega, KM compacta, señala sem_post)
→ KM reintenta crear_segmento
→ KM responde MSG_TABLA_SEGMENTOS al KS
```

**Bug 2 — Handler `MSG_FIN_COMPACTACION` envía `MSG_FIN_COMPACTACION` de vuelta al KS** — ✅ CORREGIDO

Original: `if (fd_ks >= 0) enviar_mensaje(fd_ks, MSG_FIN_COMPACTACION, NULL, 0)` — causaba un mensaje fantasma al KS.  
Fix: eliminado, reemplazado por `sem_post(&sem_compactacion_lista)`.

**Bug 3 — `list_get_index()` no existe en so-commons** (2 ocurrencias) — ✅ CORREGIDO

En `crear_segmento()` y `dessuspender_proceso()`:  
`list_remove_and_destroy_element(huecos, list_get_index(huecos, h), free)` → `list_remove_element(huecos, h); free(h);`

**Bug 4 — `leer_instruccion()` usada antes de su definición** — ✅ CORREGIDO

Agregada forward declaration `static char* leer_instruccion(uint32_t pid, uint32_t pc);` antes de `atender_cliente()`.

**#65 — STDOUT real — ✅ COMPLETADO (commit `238fb10`)**

Handler `MSG_SYSCALL_STDOUT` en `kernel_scheduler/src/main.c`:
1. Extrae `dir_logica` y `tamanio` del payload `t_payload_syscall_io_memoria`.
2. Mueve proceso a BLOCK.
3. Llama `km_request(MSG_LEER_DATOS, t_payload_acceso_datos{pid, dir_logica, tamanio})`.
4. Si `MSG_LEER_DATOS_RESP`: reenvía bytes a IO STDOUT como `[pid_n:4][bytes...]`.
5. Si `MSG_ERROR`: loguea warning (proceso queda en BLOCK, IO responderá con `MSG_IO_FIN` o timeout).

**#66 — STDIN real — ✅ COMPLETADO (commit `948b9c2`)**

- `lista_stdin_pendientes` + `mutex_stdin_pendientes`: lista global de `t_stdin_pendiente {pid, dir_logica, tamanio}`.
- `MSG_SYSCALL_STDIN`: extrae `dir_logica` y `tamanio` del payload, guarda en la lista, manda `MSG_IO_STDIN` a IO STDIN.
- `MSG_IO_STDIN_DATOS`: IO devuelve `pid` y `n_bytes` en host byte order (sin ntohl); recupera `dir_logica` de la lista, arma payload `[pid:4][dir_logica:4][tamanio:4][bytes...]` en network order y llama `km_request(MSG_ESCRIBIR_DATOS)`. Luego mueve proceso de BLOCK a READY o SUSP_BLOCK a SUSP_READY.

### Bug #1 — KS: `MSG_LEER_DATOS_RESP` no ruteado por condvar — ✅ CORREGIDO (commit `d1ed490`)

`thread_km_listener` solo enrutaba `MSG_OK`, `MSG_ERROR` y `MSG_TABLA_SEGMENTOS` a `cond_km_resp`. La respuesta de KM a `MSG_LEER_DATOS` (`MSG_LEER_DATOS_RESP`) caía en el `default` y se descartaba. Resultado: `km_request(MSG_LEER_DATOS, ...)` en el handler de STDOUT bloqueaba para siempre.

Fix: `case MSG_LEER_DATOS_RESP:` agregado al switch. La syscall STDOUT ahora funciona de punta a punta.

### Bug A — Memory Stick: no maneja `MSG_CPU_IDENTIFICACION`

**Flujo roto:**
```
CPU → MS: MSG_CPU_IDENTIFICACION {cpu_id}
MS:  case default → MSG_ERROR → close(fd_cpu)
CPU: socket_memoria_usuario = -1
Consecuencia: leer_bytes_memoria(-1, ...) = false → MOV_IN/MOV_OUT/COPY_MEM fallan
```

**Fix necesario en `memory_stick/src/main.c`:**
```c
case MSG_CPU_IDENTIFICACION: {
    uint32_t id_n; memcpy(&id_n, msg->payload, 4);
    log_info(logger, "## CPU %u Conectada", ntohl(id_n));
    enviar_mensaje(fd_cpu, MSG_OK, NULL, 0);
    break;
}
```

**Verificación de ramas de Juan Manuel:** ninguna de las tres ramas verificadas (`feature/memory-stick`, `feature/cpu/mmu`, `integracion-cpu-check3`) contiene este handler. El único cambio en `feature/memory-stick` respecto a develop es un cast de tipo en el logger (`log_level_from_string → (t_log_level)logLevel`). En `integracion-cpu-check3` el switch de `atender_cpu` no fue modificado.

### Bug B — Memory Stick: `atender_cpu` cierra la conexión después de UN mensaje

**Problema:** `atender_cpu` maneja un mensaje y llama `close(fd_cpu)`. Después de la identificación (si se arregla), la primera lectura/escritura cierra la conexión. La CPU no puede hacer una segunda operación.

**Fix necesario:**
```c
void* atender_cpu(void* arg) {
    // ...identificación...
    while (1) {  // loop por múltiples mensajes
        t_mensaje* msg = recibir_mensaje(fd_cpu);
        if (!msg) break;
        switch (msg->op_code) {
            case MSG_LEER_MEMORIA:    manejar_read(fd_cpu, msg); break;
            case MSG_ESCRIBIR_MEMORIA: manejar_write(fd_cpu, msg); break;
            default: enviar_mensaje(fd_cpu, MSG_ERROR, NULL, 0); break;
        }
        free_mensaje(msg);
    }
    close(fd_cpu);
    return NULL;
}
```

### Bug C — Memory Stick: protocol mismatch CPU→MS

**Problema:** CPU envía `MSG_LEER_MEMORIA` (36) y espera `MSG_LEER_MEMORIA_RESP` (37). MS solo maneja `MSG_MEMORY_READ` (30) y responde `MSG_MEMORY_READ_RESPUESTA` (31). El payload es idéntico — solo difieren los op_codes.

**Fix necesario:** agregar al switch del loop (Bug B) los casos `MSG_LEER_MEMORIA` y `MSG_ESCRIBIR_MEMORIA` con sus respectivos op_codes de respuesta. Los handlers `manejar_read` y `manejar_write` existentes sirven pero deben responder con `MSG_LEER_MEMORIA_RESP` y `MSG_OK` respectivamente.

**Nota:** KM usa `MSG_MEMORY_READ` (30) con `ms->fd` (conexión persistente) y eso funciona. El problema es exclusivo del camino CPU→MS.
